`release.yml` here already has the four stages the reference graph shows, under the same
names. The one node it lacks is the `dist-branches` matrix hanging off `publish`.

|                              |                                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **What this adds**           | A fifth stage: `resolve → publish → dist-branches`, one matrix job per publishable package, force-pushing its shippable files to `releases/<pkg>` |
| **What it does not touch**   | `notes`, `storybook`, the npm publish itself, `release.sh`, any package source                                                                    |
| **Reference implementation** | `invana/design-kit`'s `release.yml` (7 hand-listed packages); this is the same stage over 18, derived                                             |
| **Open decisions**           | none — D-3 and D-4 closed 2026-09-19                                                                                                              |
| **Row status**               | proposed 0 · accepted 0 · implemented 6 · landed 0 · deferred 1 · rejected 0                                                                      |

## 1 Motivation

| ID  | Observation                                                                                   | Where                                         | Evidence                                                                            |
| --- | --------------------------------------------------------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------- |
| M1  | The only install route for all 18 packages is the npm registry                                | `file:.github/workflows/release.yml#L79-L131` | `publish` is the sole distribution stage                                            |
| M2  | A consumer cannot install an unpublished or in-flight version, nor pin one without npm access | —                                             | no ref a package manager can resolve exists outside the registry                    |
| M3  | The sibling repo already solved this and its graph is the shape asked for                     | `invana/design-kit` `release.yml` stage 2     | `dist-branches`, `name: releases/${{ matrix.pkg }}`, 7 branches                     |
| M4  | The two workflows are otherwise node-for-node identical in stages and names                   | `file:.github/workflows/release.yml#L45-L241` | `Resolve target` · `Build & publish to npm` · `GitHub Release` · `Deploy Storybook` |

### Ruled out

| ID  | Hypothesis                                                                           | Verdict | Evidence                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------ | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | The whole workflow needs restructuring to match the reference                        | no      | M4 — stage set, names, fan-out and gating already match; the delta is one job                                                                    |
| R2  | A source branch (`main` itself) would serve the same purpose                         | no      | `files: ["dist"]` on all 18 and no `prepare` hook, so a git consumer of source gets nothing built and nothing that builds it                     |
| R3  | The packages need a `prepare` hook so a git install builds on the consumer's machine | no      | that pushes the whole toolchain (turbo, tsup, `@repo/*` private configs) onto the consumer; shipping built output is why the artifact exists     |
| R4  | Per-package tags (`@invana/graph@0.0.14`) would do                                   | no      | a tag is immutable per version and there are 18×N of them; a branch gives one stable moving ref per package, which is what a git dep range wants |

## 2 Design

| Step | Mechanism                                                                                                                                                                    | Evidence                                                                                                                      | Consequence                                                                                                                    |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| D1   | `resolve` additionally enumerates every non-private `packages/*/package.json` and emits `{ pkg, dir }[]` as a JSON output                                                    | 18 public + 2 private (`@repo/*`) today                                                                                       | the matrix is derived, so a new layout/layer package gets a branch by existing                                                 |
| D2   | `publish` uploads `packages/*/dist` as one artifact after its existing build step                                                                                            | `file:.github/workflows/release.yml#L110-L112` builds with the apps filtered out                                              | the branch stage reuses the published bytes instead of rebuilding — the branch and npm cannot diverge                          |
| D3   | `dist-branches` fans out over D1's list, `needs: [resolve, publish]`, `fail-fast: false`                                                                                     | —                                                                                                                             | graph shape matches the reference exactly; one package failing does not strand the other 17                                    |
| D4   | Each job assembles a clean directory: the `files[]` entries plus `README.md`/`LICENSE`, then rewrites the manifest                                                           | all 18 declare `files: ["dist"]`                                                                                              | the branch content equals the npm tarball content                                                                              |
| D5   | The manifest rewrite drops `devDependencies` and every lifecycle hook, and turns `workspace:*` into `^<version>` in `dependencies`/`peerDependencies`/`optionalDependencies` | 18× `@repo/typescript-config` + 18× `@repo/eslint-config` are `workspace:*` **devDeps**, and both are private/never published | without the drop, every git install fails resolving `@repo/*`; without the rewrite, `workspace:*` is meaningless off-workspace |
| D6   | Missing `dist/` is a hard error, not a warning                                                                                                                               | —                                                                                                                             | a failed artifact download would otherwise force-push an empty package and break consumers silently                            |
| D7   | Each job `git init`s the assembled directory and force-pushes it to `releases/<pkg>`                                                                                         | —                                                                                                                             | the branch carries one commit of built output, unrelated to `main`'s history — no source, no history growth on the main line   |
| D8   | The stage is gated on `needs.resolve.outputs.release == 'true'` like `publish`/`notes`                                                                                       | `file:.github/workflows/release.yml#L82`                                                                                      | a blank-tag dispatch still deploys only Storybook and pushes no branch                                                         |

### Confirming test

| Test | Action                                                                                                                                              | Result                                                                                                                       | Inference                                                                                                     |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| T1   | Enumerate `packages/*/package.json` locally                                                                                                         | 18 public at `0.0.14`, 2 private, all `files: ["dist"]`, zero lifecycle hooks                                                | D1/D4 hold; the hook-stripping in D5 is defensive only                                                        |
| T2   | `grep 'workspace:' packages/*/package.json`                                                                                                         | `@repo/*` only in devDeps; `@invana/*` in deps/peers                                                                         | D5's two halves are both load-bearing, for different fields                                                   |
| T3   | Check what triggers `release.yml`                                                                                                                   | `on: push: tags: v*` + `workflow_dispatch`                                                                                   | a branch push cannot re-trigger the workflow — no recursion from D7                                           |
| T4   | Resolve the install closure of the four packages the maintainer actually uses, treating non-optional peers as required (pnpm 10 auto-installs them) | 11 of 18 — adds `canvas`, `canvas-core`, `canvas-store`, `renderer-pixijs`, `canvas-react`, `graph`, `graph-layout-d3-force` | trimming the matrix saves 7 jobs at most and costs the opt-in layouts/layers their install route; D-2 settled |

## 7 Decisions

| ID  | Question                                              | Options                                                                               | Recommendation                                                                                                                                                                                                                                                                                     | Status              |
| --- | ----------------------------------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| D-1 | Hand-list the matrix or derive it?                    | literal `matrix.pkg: [...]` (reference repo) · derived JSON from the workspace        | **derive** — 18 names in YAML rot at every new layout/layer package; graph shape is identical                                                                                                                                                                                                      | accepted 2026-09-19 |
| D-2 | Which packages get a branch, and which go to npm?     | all 18 public · entry points only (5) · the maintainer's own 4                        | **all 18** — the maintainer's stated set (`canvas-ui`, `canvas-telemetry-otel`, `graph-layout-elkjs`, `graph-layer-maplibre`) has an install closure of 11 by itself (T4); the other 7 are opt-in features Storybook advertises, and the marginal cost of shipping them is one already-running job | accepted 2026-09-19 |
| D-3 | Where does the assemble logic live?                   | inline heredoc in the YAML (reference repo) · `file:scripts/assemble-dist-branch.mjs` | **in-repo script** — it is the part that can ship a broken manifest to consumers, so it should be runnable and reviewable locally (V2/V3 depend on this)                                                                                                                                           | accepted 2026-09-19 |
| D-4 | Which artifact action major?                          | `@v4` (reference repo) · match this repo's newer pins                                 | **both at `@v7`** — `upload-artifact` is at v7 and `download-artifact` at v8; matching majors keep one artifact generation, and v8 changes digest-mismatch and decompress behaviour this stage has no reason to adopt                                                                              | accepted 2026-09-19 |
| D-5 | One artifact for all 18 packages, or one per package? | single `packages/*/dist` · per-package                                                | **single** — one upload, 18 downloads; total `dist/` is small and retention is 1 day                                                                                                                                                                                                               | accepted 2026-09-19 |
| D-6 | Should the branch stage block the GitHub Release?     | sequence it before `notes` · leave both hanging off their own needs                   | **leave independent** — matches the reference graph and keeps a branch failure from withholding release notes                                                                                                                                                                                      | accepted 2026-09-19 |
