# A colour is either themed or manual, never both

Make every themed colour **resolve at paint time from a tier the theme owns**, instead of the
theme *overwriting the author's own option*. An author-set colour then wins, and keeps winning
across theme switches; an unset one follows the palette. Two spellings, deliberately different —
`sym:BackgroundLayer` has one tier so it needs the explicit sentinel **`'inherit'`** (F1–F6);
`sym:GraphLayer`'s node/edge styles already have a four-tier cascade, so **absence is the
sentinel** and the fix is to slot the theme *underneath* the author (F7–F11), with `'inherit'`
accepted only as a *patch* value meaning "clear this back to the theme".

| | |
|---|---|
| Problem | `sym:BackgroundLayer.adoptTheme` (`file:packages/canvas/src/layers/BackgroundLayer.ts#L369-L381`) **overwrites** `this.opts.backgroundColor` / `this.opts.color` on every `theme:change`. An author-set colour survives until the first theme publish, then is gone — permanently, with no record it was ever set |
| Root cause | Theme adoption is modelled as **mutation of the options** rather than **resolution at paint time**. Once the option is overwritten, "themed" and "authored" are indistinguishable — there is no value the author can write that means *defer to the theme* |
| Same defect, one level deeper | `sym:GraphLayer.applyTheme` (`file:packages/graph/src/layer/GraphLayer.ts#L573-L596`) calls `setNodeDefaults` / `setEdgeDefaults`, which write the palette **into `this.nodeOption.style`** — the very object the author configured. An authored `labelColor` is destroyed on the first theme publish |
| Worse for groups | `sym:paletteToGroupStyle` is written into **each group node's own `style` in the store**, so the theme's hexes are exported as node data by `sym:exportCanvasState` and reload pinned |
| The ask | A CSS-like `inherit`: unset ⇒ the theme's role; set ⇒ mine, permanently. Explicitly extended to **node and edge label text** (`labelColor` ← `foreground`) |
| Non-goal | New palette roles, a new theme family, reading design-kit CSS variables for `surface` (only `accent` bridges to CSS today — separate ask), or the per-type styling templates, which already resolve roles correctly and are the model being copied |
| Row status | rows: **implemented 6** (F1–F6, the background) · **proposed 7** (F7–F11 the graph, F13–F14 the naming + absence) · **deferred 1** (F12) · verification: **pass 1 · pending 13** (V1–V8 are browser checks the implementing session can't run) · decisions: **accepted 4** (D-1 … D-4, all as recommended) · **open 4** (D-5 · D-6 · D-7 · D-8) |

## 1 Motivation

| ID | Observation | Where | Evidence |
|---|---|---|---|
| S1 | Setting `backgroundColor` on a canvas that has a `sym:ThemeBehaviour` in the named-palette path is silently a no-op from the first theme publish onward | `file:packages/canvas/src/layers/BackgroundLayer.ts#L374-L376` | `const surface = palette[this.opts.surfaceRole]; if (surface !== undefined) this.opts = { ...this.opts, backgroundColor: surface }` — unconditional, no check for an author-set value |
| S2 | The workaround in the wild is to **disable the theme entirely**: `story:canvas-ui/apps/GraphCanvasApp/CustomComposition` passes `bundle={false}` and says so in a comment | `file:apps/storybook/stories/canvas-ui/apps/GraphCanvasApp/CustomComposition.stories.tsx#L33-L54` | "With `bundle` off there's no engine ThemeBehaviour, so the canvas colours are fixed here" — a whole bundle turned off to keep two hexes |
| S3 | The other workaround is `surfaceRole: '<a role that does not exist>'`, which is undiscoverable and reads as a bug to the next person | `file:packages/canvas/src/layers/BackgroundLayer.ts#L104-L108` | The TSDoc documents the override, but the only opt-out is naming a missing role |
| S4 | The overwrite **launders the theme's colour into the authored state**: the settings panel seeds from `getOptions()`, so the theme hex becomes the form value, and applying any unrelated field (spacing, alpha) writes that hex into `view.definition` as if the author had chosen it | `file:packages/canvas-ui/src/editor-panels/canvas-settings/CanvasSettingsEditorPanel.tsx#L35-L47` (`sym:readOptions` prefers `getOptions()`) + `file:packages/canvas-ui/src/editors/layers/background-layer/mapping.ts#L45-L60` (`sym:formToOptions` emits every set field) | After one theme flip + one panel Apply, the canvas is pinned to whatever the theme happened to be at that moment — and stops following the theme |
| S5 | There is no way to theme *one* of the two colours — take `surface` from the theme but pin the dot colour, or vice versa. It is all-or-nothing per layer | same as S1 | Both roles are adopted in the same method with the same unconditional write |

| S9 | `story:canvas-ui/apps/GraphCanvasApp/CustomComposition` sets `labelColor: 0xe2e8f0` on its nodes — and can only keep it by disabling the whole bundle (S2) | `file:apps/storybook/stories/canvas-ui/apps/GraphCanvasApp/CustomComposition.stories.tsx#L62-L68` | The same story is evidence for both halves of this RFC: authored backdrop **and** authored label colour, both defended by turning the theme off |
| S6 | The editor exposes `surfaceRole` / `patternRole` as free-text fields but no control for "themed vs custom", so the panel cannot express the state the engine is actually in | `file:packages/canvas-ui/src/editors/layers/background-layer/fields.ts#L79-L82` | `THEME_FIELDS` is two `type: 'text'` inputs; the colour swatch above it silently disagrees with them |

### Ruled out

| ID | Hypothesis | Verdict | Evidence |
|---|---|---|---|
| R1 | The 39 stories that set an explicit `backgroundColor` are already broken by this | **No** | They use the **single-layer shorthand** (`targetLayerId: 'bg'` + flat `light`/`dark` patches), which publishes an **empty palette** on purpose (`file:packages/graph/src/behaviours/ThemeBehaviour.ts#L20-L24`), so `adoptTheme` finds no role and returns early. Only the 7 named-palette story files are in scope |
| R2 | `mode: 'light' \| 'dark'` is the escape hatch | **No** | `mode` selects the branch of a `{ light, dark }` **pair** (`sym:BackgroundLayer.resolveColor`); it does not stop `adoptTheme` from replacing the whole option with a scalar |
| R3 | Provenance tracking (remember which keys the author set, theme fills only the rest) would work | **Rejected, not wrong** | It works in-process and dies on serialisation: `view.definition.layers.bg.options` carries values, not provenance, so a reload or a collaborative sync loses the distinction. An explicit sentinel round-trips (D-1) |
| R4 | This is a `pkg:@invana/graph` styling-template problem | **No** | Per-type templates already resolve roles → numbers at compile time against `sym:GraphLayer.themePalette` (`file:packages/graph/src/layer/GraphLayer.ts#L604-L616`) and never overwrite an authored value. The defect is in the *base defaults* path (F7), not the template path |
| R6 | Node/edge styles need the `'inherit'` sentinel too, symmetrically with the background | **No — and this is the design decision** | `sym:resolveNodeStyle` (`file:packages/graph/src/layer/GraphLayer.ts#L980-L1005`) is already a documented four-tier cascade (layer template → per-type binding → per-node → states). In a cascade, **absence already means inherit** — CSS's own rule. The defect is only that the theme writes *into* the author's tier instead of sitting *below* it (G8) |
| R7 | Per-type styling templates are affected | **No** | `sym:resolveTypeBinding` resolves roles against `sym:GraphLayer.themePalette` at compile time and returns a fragment that is merged, never written back (`#L605-L615`). It is the correct pattern already — G8 makes the base tier behave the same way |
| R5 | `sym:BackgroundLayer` writes the theme colour into the serialised definition | **No** | `adoptTheme` mutates only the layer-local `this.opts`; `view.definition` is written by `canvas.update()`. The leak into authored state is **indirect**, via the editor round-trip (S4) — which is why it is easy to miss |

## 2 Design

| Step | Mechanism | Evidence | Consequence |
|---|---|---|---|
| G1 | Move theme adoption from **write-time** to **read-time**: `theme:change` triggers a repaint, not an option rewrite | `sym:BackgroundLayer.paint` already re-resolves colours on every call (`file:packages/canvas/src/layers/BackgroundLayer.ts#L296-L312`); resolution is cheap and already happens per camera event | The options object stops being a mixture of authored and derived values. `getOptions()` returns what the author wrote — which fixes S4 with no editor change |
| G2 | The sentinel is a **value in the option**, not a flag beside it: `'inherit'` joins the `BackgroundColor` union | `BackgroundColor` is already a union of `number \| string \| { light, dark }` (`file:packages/canvas/src/layers/BackgroundLayer.ts#L52-L55`); a string literal member costs nothing | Serialisable, so it survives export/import and a future CRDT sync (R3); JSON-visible, so the editor can render it as a mode |
| G3 | `'inherit'` resolves through the **role the layer already declares** (`surfaceRole` / `patternRole`), not a new mapping | Those options exist and are documented (`#L104-L118`) | No new vocabulary: `'inherit'` means "the role I am configured to read". Changing which role is a separate, existing knob |
| G4 | The sentinel + resolver live in `pkg:@invana/canvas-core`'s theme module, not in the layer | `file:packages/canvas-core/src/state/theme/types.ts` already owns `sym:ResolvedTheme` / `sym:ThemeState`, and core is the floor every other package re-exports | One implementation for F7 (`sym:GraphLayer`) and for any future themed option, instead of a second copy of the same three lines |
| G5 | A **concrete fallback** is still needed for "no theme published yet" — `'inherit'` cannot paint nothing | `sym:BackgroundLayer` mounts before any behaviour enables; `ctx.theme.current()` is `null` until the first publish | Today's `DEFAULTS` hexes (`#f8fafc` / `#6f7b8b`) survive as the *fallback*, not as the *default option* — so a canvas with no `sym:ThemeBehaviour` looks exactly as it does today (V3) |
| G6 | The `{ light, dark }` pair form composes with the sentinel: `{ light: 'inherit', dark: '#000' }` resolves the branch first, then the sentinel | `sym:BackgroundLayer.resolveColor` is already two-stage (`#L364-L367`) | Pin one kind, inherit the other — the finest granularity anyone has asked for, for free |
| G7 | The single-layer shorthand path is unchanged: it calls `layer.setOptions(patch)` with concrete hexes, which is an ordinary authored write | `file:packages/graph/src/behaviours/ThemeBehaviour.ts#L20-L24` | The 39 shorthand stories keep their exact pixels (R1, V4). The shorthand permanently replaces `'inherit'` on that layer, which is the honest reading of an explicit `setOptions` (D-3) |

| G8 | For node/edge styles the fix is a **new lowest tier**, not a new value: `sym:resolveNodeStyle` / `sym:resolveEdgeStyle` merge a private `themeNodeStyle` / `themeEdgeStyle` (rebuilt on each publish from `sym:paletteToNodeDefaults` / `sym:paletteToEdgeDefaults`) *before* the layer template, and `applyTheme` stops calling the setters | The cascade and its precedence are already explicit and documented at `#L960-L969`; adding tier 0 is one `assignNodeStyle` call per resolver | An authored `labelColor` survives every theme switch; an unset one follows `foreground` — with **no change to `sym:NodeStyle` / `sym:EdgeStyle`**, so nothing new can reach the renderer |
| G9 | `'inherit'` is **config vocabulary, never spec vocabulary** — it is legal in an options patch and is resolved (and erased) at the layer boundary; `sym:NodeStyle.labelColor` stays `number` | The existing invariant is stated at `#L602-L603`: "All colour roles are resolved against the current palette here, so nothing role-shaped reaches the renderer" | The renderer contract, the spec types in `pkg:@invana/canvas-core`, and every serialised *spec* stay exactly as they are. Only the **patch** type widens |
| G10 | `'inherit'` still earns its place in the cascade — as the only way to **un-set** through a merge-only API. `setNodeDefaults({ labelColor: 'inherit' })` deletes the key from the author's tier rather than storing a value | `sym:setNodeDefaults` merges (`#L804-L811`); there is no other way for an editor form or a `canvas.update()` patch to say "stop pinning this" | The editor's *Theme / Custom* toggle (F5) works identically for the background and for node/edge labels, on top of two different mechanisms |
| G11 | The theme tier must be merged with an **undefined-skipping** assign | `sym:assignNodeStyle` is `Object.assign` (`#L2749-L2757`), so a higher tier carrying an explicit `labelColor: undefined` would wipe tier 0 — a trap that does not exist today, because today there is no tier below the author | Prune undefined keys when merging tier 0 upward, or the theme will intermittently vanish depending on how a caller built its style object (V12) |

| G12 | Absence and the sentinel are **not redundant**: absence covers *authoring*, the sentinel covers *un-authoring*. `setOptions` merges (`{ ...this.opts, ...changes }`) so a patch cannot delete a key; `view.definition` is serialisable (`sym:assertSerialisable`) and `JSON.stringify` drops `undefined`, so "un-pin" has **no serialisable spelling** without a value that means it | `sym:formToOptions` omits `undefined`/empty keys, so the editor's Theme toggle would emit *nothing* and silently fail to un-pin | Keep both: absent ⇒ inherit (F14, so the sentinel is never typed by hand), `'inherit'` ⇒ inherit (the only way an editor, a `canvas.update()` patch, or an imported document can say "go back to the theme") |

## 7 Decisions

| ID | Question | Options | Recommendation | Status |
|---|---|---|---|---|
| D-1 | What spells the sentinel? | (a) `'inherit'` — CSS's word, what was asked for · (b) `'theme'` — says where it comes from · (c) `{ role: 'surface' }` — an object, arbitrary role per option · (d) provenance tracking, no sentinel (R3) | **(a) `'inherit'`**. It is the word every author already knows, it is serialisable, and the role indirection already exists as `surfaceRole` / `patternRole` so (c) buys nothing. (d) does not survive serialisation | **accepted** — `'inherit'`, as recommended |
| D-2 | Should the no-theme fallback stay one hex, or become a `{ light, dark }` pair? | (a) Keep `#f8fafc` / `#6f7b8b` regardless of `mode` — today's behaviour exactly · (b) Fall back to a light/dark pair so `mode: 'dark'` with no theme published isn't a white page | **(b)**, with (a)'s light values unchanged — so V3 stays pixel-identical for the default `mode: 'auto'` and only the explicitly-pinned-dark-with-no-theme case improves | **accepted** — `{ light, dark }` fallback pair, light values unchanged |
| D-3 | Should the single-layer shorthand's `setOptions` push be able to overwrite `'inherit'` permanently? | (a) Yes — it is an ordinary authored write (G7) · (b) No — mark shorthand pushes as derived and restore `'inherit'` when the shorthand is removed | **(a)**. The shorthand is documented as a migration aid for imperative stories; adding a second provenance channel to preserve it re-introduces exactly what R3 rejects | **accepted** — the shorthand's `setOptions` is an ordinary authored write |
| D-4 | How does the editor render the choice? | (a) A `Source` select (`Theme`/`Custom`) sharing a row with the swatch, swatch hidden when themed · (b) A preset swatch labelled "Inherit" inside the existing colour field · (c) Empty value = inherit, explained in the description | **(a)**. (b) needs the colour widget to render a non-colour, (c) is invisible — and (a) is the only one that also shows *which* role is being inherited, next to the existing `surfaceRole` field | **accepted** — a `Source` select sharing a row with the swatch |

| D-5 | Node/edge styles: explicit `'inherit'` sentinel, or a theme tier under the cascade? | (a) Tier 0 under the author, absence = inherit (G8), `'inherit'` only as a patch verb (G10) · (b) Widen `sym:NodeStyle` colour fields to `number \| 'inherit'` and default them to `'inherit'`, symmetric with `sym:BackgroundLayer` · (c) Both | **(a)**. (b) widens a public style type at every colour field, forces a resolution pass before every spec emit, and re-opens the "nothing role-shaped reaches the renderer" invariant — to express something the cascade already expresses by absence. The asymmetry with the background is not an inconsistency: the background has **one** tier, so it has no absence to mean anything | open |
| D-6 | What happens to group-node styles already baked into exported documents (S8)? | (a) Leave them — they open pinned, like any other authored colour (D6) · (b) Strip `cardBg`/`divider` from group nodes on import · (c) Version the export and strip only for documents written before this change | **(a)** now, **(c)** if it bites. (b) would delete deliberately-authored group colours, and today's format cannot tell the two apart — the same ambiguity as D6 | open |
| D-7 | Does the *whole* role map move to tier 0, or only label text? | (a) All of `sym:paletteToNodeDefaults` / `sym:paletteToEdgeDefaults` (label text, node border, edge stroke, arrowheads) · (b) Only `labelColor`, leaving the rest overwriting | **(a)**. They share one code path and one defect; splitting means two mechanisms and a second migration later. The ask named label text, but the fix is not smaller if scoped to it | open |

| D-8 | Is the role rename (F13) breaking, and does it need aliases? | (a) Hard rename, no alias · (b) Rename with `surfaceRole` / `patternRole` kept as deprecated aliases for a release · (c) Leave the names alone | **(a)**. The repo is pre-1.0 (`0.0.12`), the options have **zero** consumers outside the layer and its editor (no story, no app, no other package), and the two hits in `apps/docs/api/` are generated TypeDoc that regenerates. An alias would preserve a name whose only virtue is that it was there first | open |
