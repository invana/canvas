- [required-type-on-records-rfc.md](./required-type-on-records-rfc.md) — **`type` becomes required on the stored `GraphNode` / `GraphEdge`** (📋 proposed; approach locked). Readers get a guaranteed `string`; the optionality is confined to a new `GraphNodeInput` / `GraphEdgeInput` at the `setData` boundary, with `GraphStore.installNode` / `installEdge` defaulting to `'unknown'`. Chosen over requiring every author to write it, which was **measured**: 141 compile errors in `@invana/graph`, **11 of ~24 dataset exports** needing edits (incl. `h1b2019AsGraph` at 24,683 nodes), and **232 of 301 storybook files** that build records inline — versus ~6 files for the store-boundary default. Key finding: the input/stored split is **already documented** (`data-types-instances.md`) and **already declared** (`NodeData` / `NodeInput`) but **never wired** — `GraphData.nodes` is `GraphNode[]` and neither declared type has a single runtime user, so this finishes an existing split rather than inventing one. Locks `UNKNOWN_TYPE = 'unknown'` as a named export and normalises with **`||` not `??`** on **both** insert paths, so `type: ''` can't satisfy the type system and defeat the purpose. `ColorByBehaviour` treats the sentinel as **`fallbackColor`, not a palette category**, so every untyped dataset looks exactly as it does today and *"grey means no information"* stays true — the accepted cost being that `UNKNOWN_TYPE` becomes a reserved string. `exportData` **omits** `type` when it equals the sentinel, so the rule is symmetric: *absence of `type` means `UNKNOWN_TYPE`, in and out*. **§6** scopes the dead `NodeData`/`NodeInput`/`EdgeData`/`EdgeInput`/`GraphDataOptions` cluster — a closed loop with zero runtime users, delete not wire, landable independently. **§7** traces all six serialization paths: old snapshots need **no migration** (typeless records normalise on import), but new ones gain ~1 MB of `"type":"unknown"` padding on the largest dataset, so export should omit `type` when it equals the sentinel. 9-item work register.

## Performance & scale

- [large-graph-performance-plan.md](./large-graph-performance-plan.md) — **rendering perf on large, crowded graphs** (the ~5k-node / ~28.6k-edge "hairball"): the symptom, the telemetry-measured root cause (no viewport culling + one `Graphics` per edge → ~110k display objects re-rendered every frame; the `layers` phase dominates pan/drag/layout; loose edge bboxes make hover hit-test expensive), the **zoom-regime framing** (culling wins zoomed-in; batching + LOD win zoomed-out; neither is universal), the render options (A culling · B edge batching · C zoom-LOD · D cache path samples · E gate edge hit-test by zoom · F frame-coalesced flush · G hover fast-path), and — for **hovering the *right* edge in a crowd** — the edge-pick **correctness** analysis (nearest-wins is technically right but flickers / is ambiguous / invisible when edges are near-coincident) with its own options (H segment-level hit index · I stable nearest + hysteresis · J node-incidence bias · K node-hover-first · L ambiguity picker) and the "reliable-when-separable, graceful-when-not" stance. Recommended phasing: cheap standalone wins + edge-pick stability first → segment index → culling → batching/LOD. Companion to the `feat/canvas-telemetry-otel` observability work.
- [render-pipeline-plan.md](./render-pipeline-plan.md) — **how render work is expressed, merged, ordered and paid for**. Today there is no pipeline: a store event calls the renderer imperatively and immediately (`GraphLayer`'s flush handler is a hand-rolled miniature of the right idea — four dirty sets drained in a prose-documented order). Proposes a **render-intent queue**: producers `mark(id, class)` instead of calling the renderer; intents coalesce on `(id, class)` via an explicit merge matrix; a **frame planner** orders them by **cost class** (`move` ~0.05 ms → `geometry` high — a 100× spread today invisible to callers) under an **interaction-aware budget**, so cheap work always runs at 60 fps and only expensive classes slip. Adds the dependency-ordering contract (remove → install → move → frames → geometry → route → restyle → decorations), a **bulk lane** (machine-rate work skips per-item events — the kernel's own two-lane doctrine, extended from positions to install/update), **epochs** for one-compare invalidation, and **backpressure** with a degradation ladder. §8 answers the worker question: layout / ingest / derived geometry / index build / vertex-buffer construction move off-thread; **rendering itself doesn't** (OffscreenCanvas relocates the freeze and costs input latency — but the `IRenderer` extraction makes a worker renderer just another implementation, so the option stays open). Phased R0–R5 + W1–W3, with risks (R2 is a behaviour-preserving refactor of code that works) and the over-abstraction check.
- [large-graph-load-pipeline-plan.md](./large-graph-load-pipeline-plan.md) — **initial-load perf** (the disjoint half of the perf plan), written as a *consumer* of the render pipeline: loading ~5k nodes / ~20k edges freezes the tab for seconds *before any layout*, because `GraphLayer` installs every element inline in one unbroken macrotask (`addShape` → Graphics + rbush + label `Text`; `addConnector` → Container + 3 `Graphics` + a full route). Culling and frame-coalesced flush can't help — the cost is *constructing* the instances. Key framing: **budgeting alone gives non-blocking, not snappy** (same 2–4 s, now as popcorn), so it takes three levers — **yield** (install as a deferrable intent class, nodes before edges, epoch per load, sync threshold), **cut** (install-time LOD: skip sub-pixel label `Text`, `keepFraction` edges, badges, unrouted connectors — the largest single win, and the on-ramp to virtualization), and **order** (camera-fit from *store* bounds → node bodies → edges → labels: progressive **fidelity**, not progressive elements; a live canvas + progress chip, never a spinner). Plus edge-install staged against layout cool-down. Records the partial-render hazards (`getBounds`/`fitOnLoad` read the renderer, cull invalidation, `exportImage`, headless), the honest ceiling (25k display objects cost what they cost → virtualization / edge batching next), and phases L0–L6.

## Engine features

- [autofit-bounds-rfc.md](./autofit-bounds-rfc.md) — 📋 **`fitOnLoad` frames the wrong box.** The camera lands zoomed into the gap between two nodes (4400 % on the GraphVisualiser, 2750 % on `FullFeatured`, a blank `d3-hierarchy/Tree`), which reads as "the nodes aren't rendering" — four such reports in one session, every one a camera bug over a correctly-drawn scene. Established: `GraphLayer.getBounds()` measured a **7 × 7** rect (one node of `radius: 3.5` — i.e. 252 nodes still stacked at the origin) while the graph was visibly spread out, and fitting that into a 1200 px viewport *is* the 4400 %; an **animated** force sim self-corrects because `_armAutoFit` re-fits on every `layout:run:tick`, while a one-shot layout (`animate: false`, d3-hierarchy, sankey, ELK) gets exactly one shot and keeps the stale box. Not yet established — and the reason this is an RFC rather than a patch: the write path *looks* synchronous (`setPositionsBulk` → `store.flush()` inside `getBounds` → `node:update` → `moveShape` mutating `spec.x/y` in place, the very fields the bounds read), and the two failures disagree (Les Mis self-corrects seconds later = one-frame race; the hierarchy case still read 7 × 7 two seconds on = positions never reached the specs). Plan: one instrumented run whose three outcomes each name their own fix site (`_armAutoFit` wiring · `fitView` · the store→layer bridge), then a ≤20-line change on the principle that **a measurement must not depend on frame ordering** — explicitly *not* re-timing `fitView`, which the Fit button, `fitOnLoad` and the layout wrappers all share. Outcome C would mean `getShapeWorldBounds` can disagree with the store for bulk writes, which affects hit-test bounds / minimap / ELK sizing too, and re-scopes this.

- [group-aware-layouts-plan.md](./group-aware-layouts-plan.md) — **make `parentId` groups lay out correctly in every layout, not just ELK**. Today only ELK does containment (opt-in), d3-force approximates it (centroid pull), geometric/sankey ignore it, and `D3HierarchyLayout` **crashes** (its tree comes from *edges*, so a frame node is a second root). Three root causes: every hierarchy-aware layout conflates `parentId` with "group" (a group is `style.group`/`isGroupNode` — so plain **trees** get boxed), collapse-hiding is *derived* via `collapsedAncestor` so `shouldPlaceNode`'s `hidden` test misses collapsed members everywhere, and each layout owns private copies of the rules. Fix: shared helpers in `@invana/graph` (placeable predicate · `effectiveEndpoint` edge remap+dedupe to a fixpoint · `GroupOptions` insets), then **ELK native compound** (fix + collapse the flat/compound branches into one + default `includeGroups: true`) · the d3-hierarchy crash fix · a **`RecursiveGroupLayout`** (lay each group out in isolation → box → super-node at the parent level → translate) that gives grid/circular/tree/radial containment for free. Records the two meanings of "group support" (native vs recursive) and recursion's blind-subgraph quality caveat.
- [per-element-visibility-plan.md](./per-element-visibility-plan.md) — **first-class per-element hide/show** for nodes & edges (single + batched bulk), a `hidden` flag stored as a `flags`-column bit (sibling of `pinned`) with the effective-visibility rule (edge hidden if an endpoint is) owned by `GraphStore`. Culls from render/hit-test/bounds/camera/layout/labels/minimap (not `alpha 0`), fixing invisible-but-clickable; `node:visibility`/`edge:visibility` events (derived-only incident-edge cascade), serialization round-trip, and `Layer.setVisible` + `scene:layer:visibilitychange` for whole-layer visibility.
